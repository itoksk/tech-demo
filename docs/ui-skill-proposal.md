# UIスキル最適化案

確認日: 2026-09-06。対象はローカルの `ui-ux-pro-max/SKILL.md`、`references/design-craft.md`、`references/shig-principles.md`、`liftkit-design-principles/SKILL.md` とカラー参照です。既存のインストール済みスキルは変更していません。

## 結論

全面的に古いというより、**特定のWeb表現の好みが、汎用UIの絶対ルールになっている**ことが問題です。近接・整列・一貫性・ユーザーの主導権・実画面の検証は残し、媒体別の判断と現在の実装環境に合わせるのが適切です。

今回の旧エンジン画面では、文字・余白の整備に対して「外形の認識」「機構の説得力」「観察と操作の同時性」が弱くなりました。これはスキルの年齢だけでは説明できず、3D教材の目的を優先する設計ルールが不足していたこと、実装側の題材表現が不足していたことの両方が原因です。

## 優先する変更

| 優先度 | 現状 | 提案 | 理由・検証方法 |
|---|---|---|---|
| P0 | タイポグラフィを常に主役にし、ヒーローを68〜110px相当にする | LPは訴求、業務UIは作業、3D教材はモデルと因果関係を主役にする | 1280×720で観察対象と主要操作を同時に確認できるか |
| P0 | WCAG 2.1中心の記述 | WCAG 2.2 AAを基準に、ドラッグ代替、フォーカスの遮蔽、ターゲットサイズも扱う | 視点ボタン、拡大縮小ボタン、キーボードでスライダーを操作する |
| P0 | Lighthouse 100点を必須品質ゲートにする | 自動検査と手動タスク検証を分ける | スコアに含まれない手動項目を別途確認し、実施範囲を記録する |
| P0 | 黄金比のcaptionが約0.62rem＝約10px、本文行間1.272 | 文字・余白・操作面積を別スケールにする | 日本語本文16px/1.7前後、補助13px前後を出発点に、実サイズで読む |
| P1 | `app/globals.css` とトークンが存在する前提 | 実際のCSS・既存デザインシステムを発見してから適用 | Viteでは既存のstyle.cssも尊重。存在しないファイルを要求しない |
| P1 | TailwindのJS設定例のみ | 使用バージョンを確認し、v3とv4の例を分ける | v4はCSSベースの `@theme`、v3は既存のJS設定に追従 |
| P1 | 紫青、純黒純白、左帯、カード枚数などを一律禁止 | ブランド色、意味、可読性、情報構造に対する判断にする | 色や装飾そのものを不適合判定の根拠にしない |

| P2 | 対応不要でもlight/dark両方を要求 | ユーザーの要件に必要なテーマのみ | 意味色とon-colorの対はテーマごとに確認する |

## 基準の扱いを正確にする

- WCAG 2.2の2.5.8はAAで24×24 CSS pxを基本とし、間隔や等価な操作手段などの例外があります。44pxはタッチ操作の有用な設計目標ですが、AAの一律最低値という書き方は避けます。[W3C: Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- ドラッグ機能には、原則としてドラッグを必要としない単一ポインター操作の代替も用意します。キーボード対応だけで代替要件を満たしたと判断しません。[W3C: Dragging Movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)
- Lighthouseのアクセシビリティスコアに手動監査は含まれません。100点でも、操作の完了、理解、Canvas内容の同等な情報提供は別に確認します。[Chrome: Accessibility scoring](https://developer.chrome.com/docs/lighthouse/accessibility/scoring)
- 大きい文字のコントラスト例外は18pt（24 CSS px）、または14ptの太字（約18.67 CSS px）が目安です。現在の「18px bold」は丸めすぎです。半透明文字の `white/80` だけで合格を保証せず、合成された背景に対して確認します。[W3C: Contrast (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)
- Tailwind v4はCSSのテーマ変数を中心にする構成があります。JS設定例は削除するのでなく、v3向けとして位置づけます。[Tailwind: Theme variables](https://tailwindcss.com/docs/theme)
- LiftKitは独立した上流プロジェクトとして進化しています。ローカルの数学原則の抜粋を、現行コンポーネントAPIの仕様だと扱わないようにします。導入時に上流とバージョンを確認し、比率そのものが読みやすさを保証すると主張しません。[Chainlift/liftkit](https://github.com/Chainlift/liftkit)

## ui-ux-pro-max の本文改訂案

以下は置き換え可能な本文の方向性です。まだインストール済みファイルには適用していません。

```markdown
# UI/UX設計と検証

ユーザーが対象を理解し、操作を完了できる画面を作る。
既存のブランド・実装・明示された要件を優先する。

## 最初に判断する

- 対象は、説明ページ、作業UI、教材、可視化のどれか。
- ユーザーの中心行動と、その完了を示す結果は何か。
- 主役は文章、対象物、データ、操作のどれか。
- 実際の技術構成、トークン、制約を確認する。

## 構成

関係する操作と結果を近くに置く。説明は必要な時に開示する。
カード、配色、書体、余白の数を一律に規制しない。
装飾を選ぶ際は、意味、認識、操作、ブランドに対する効果で判断する。

## アクセシビリティ

WCAG 2.2 AAを検証基準にする。
適用する達成基準と、プロジェクトの推奨値を区別する。
ラベル、フォーカス、コントラスト、拡大、キーボード、
ドラッグの代替、モーション設定を実際の画面で確認する。
自動スコアだけで適合を断定しない。

## 3D・教材の場合

最初の画面で対象と主要操作を見せる。
外観から対象を認識できるようにし、内部表示へ移行できるようにする。
操作値、3Dの変化、数値、説明を同じモデルの状態から更新する。
誇張・模式化・省略・時間倍率・単位を明記する。
Canvasのクリックだけに依存せず、部品の選択ボタンを用意する。
再生停止、視点復帰、全体が見える初期カメラを用意する。

## 検証

代表タスク、初期値、端点、狭い画面、200%拡大を確認する。
表示上の不具合はスクリーンショットで確認する。
数式のある教材は保存則や単調性などを独立に検証する。
未検証項目は未検証として記録する。
```

共通本文には判断を変えるルールだけを残し、LPの表現、業務画面、3D教材、アクセシビリティの具体例は各参照ファイルへ分ける案です。「AIっぽい」という主観的判定は診断の補助とし、合否基準にはしません。

## liftkit-design-principles の本文改訂案

```markdown
# 比率を使ったデザイントークン

黄金比は、候補となるスケールのひとつ。
既存トークンと読みやすさを優先し、比率を全要素に強制しない。

## 分けて設計する

- 文字：本文、補助、見出し、表示用数字を役割で定義する。
- 余白：4px/8px刻みやφスケールから用途に合う候補を選ぶ。
- 操作面積：文字サイズとは別に入力方法に合う最小寸法を持つ。
- 色：surface/on-surfaceなど、背景と文字の対を定義する。

## 既定値の候補

日本語本文 1rem、行間1.7、補助0.8125remを出発点にする。
操作用文字は0.875rem程度、頻用するタッチ操作は44pxを目安にする。
見出しの比率は1.2〜1.333程度から検討し、
大きな広告的見出しが必要な時にφも選択肢とする。
値は規格ではなく、対象ユーザーと実画面で確認するための候補。

## 実装

フレームワーク・CSSの配置・バージョンを先に確認する。
CSS変数、Tailwind v3、Tailwind v4の方法を混同しない。
remとclampを活用し、狭い画面と文字拡大でも操作を保つ。
必要なテーマだけを作る。色対は実際の背景で確認する。

## 検証

算出値を目で確かめ、理由があれば丸める。
円を一律に拡大するなどの補正値は固定規則にしない。
上流のAPIを使う場合は採用バージョンの公式情報を確認する。
```

## 今回のアプリで反映したこと

- 観察対象を主役にし、導入文の面積を縮小。
- デスクトップでは3Dを画面内に維持し、操作パネルを独立してスクロール。
- モバイルは縦積み、画面比率に合わせたカメラでモデル全体を表示。
- 文字の役割別トークンを追加し、説明と操作文字を拡大。
- ドラッグ以外の視点変更・拡大縮小ボタンを追加。
- CVTの出力メーターをモデル上にも表示し、変速操作と結果を同時に観察。
- 3Dのモデル計算を分離し、CVTのベルト長とBJTの電流保存などをテスト。

## 段階的な適用

1. P0項目を改訂案に反映し、現在の規範・推奨・個人の好みを分離。
2. 3D教材、通常のフォーム、LPという異なる題材で同じスキルを試す。
3. 操作完了、可読性、モデルの理解を観察し、悪化した項目を修正。
4. 効果を確認した後にインストール済みスキルを更新する。

今回提示するのは改訂案です。スキル全体の正式更新や、アクセシビリティ規格への全面適合認証は実施していません。
